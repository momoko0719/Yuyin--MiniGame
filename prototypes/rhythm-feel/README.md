2. **砍在拍子上，爽不爽？** — 打击的爽和卡上拍子的爽能否合成同一种快感 → ✅ 已验证

> 本项目原型阶段用它们做手感验证，但不随代码分发。

> ```bash
> python tools/analyze_song.py <你的音频>
> python tools/make_songmap.py <auto.songmap.json> "0:intro,<副歌秒数>:chorus"
> python tools/make_envelope.py <你的音频> <songmap.json>
> ```
> 随仓库提供的 `bei_qu_yi_dao.ogg`（Suno 生成，无版权顾虑）可以直接用。
> 节拍器音轨用 `python tools/make_click_track.py` 重新生成。
>
> **谱面数据（`charts/`）是保留的**——那是本项目真正的劳动成果。


在 Godot 4.7.2 中打开 `prototypes/rhythm-feel/rhythm-feel/`，按 F5。
**主场景是 `song_fight.tscn`**——曲式驱动的完整战斗，读取手工编排的谱面。

| 键 | 作用 |
|---|---|
| 空格 | 斩 |
| J | 格挡 |
| `[` `]` | 判定校准 −5ms / +5ms（实时生效，屏幕显示当前值） |
| `0` | 校准归零 |
| `1` / `2` | 切换谱面来源：1=手敲，2=自动初稿 |
| R | 重来 |
| ESC | 退出 |

演示内容为手工编排的 **14 段谱面**（137 个事件，覆盖到第 216 拍 / 约 112 秒）。
打完最后一个音符后 10 秒淡出进入结算画面，不会傻等整首歌播完。

## 已确认的发现

### 1. 音频时钟：假设成立 ✅

开发机（RTX 5070 Laptop，165Hz）实测：

| 指标 | 实测值 |
|---|---|
| `AudioServer.get_output_latency()` | 10.00 ms（低于 Godot 默认 15ms，无需调整） |
| 混音率 | 48000 Hz |
| 渲染帧计时 30 秒累计漂移 | **+12.4 ms**（已差出整整一拍） |
| 时钟抖动丢弃率 | 约 15%（749 / ~4950 帧） |

官方推荐公式
`get_playback_position() + get_time_since_last_mix() - get_output_latency()`
加单调性防抖，精度足够。渲染帧计时会线性累积漂移，一首 3.5 分钟的歌会漂到
约 87ms —— **确认不能用帧计时**，必须用音频播放位置。

### 2. 判定窗口必须比标准音游宽得多 ✅

人工敲击实测波动（标准差）**±29.5 ms**，而标准音游 Perfect 窗口是 ±16–30ms
—— 按那个标准开发者本人都打不准。这是人类 + 键盘 + 系统的固有抖动，技术上消不掉。

采用：**Perfect ±60ms / Good ±120ms / 空挥不惩罚**，直接对应支柱一
「节奏决定你打得多狠，不决定你死不死」。

两种敲击手法（抬手 vs 贴键）：**靠宽判定自然容纳，不做模式选择**——
让玩家自己选模式等于让他为自己的选择买单。

### 3. 顿帧量化到音符时值：假设成立 ✅

顿帧时长用音符时值定义而非秒，顿帧结束的那一刻正好落在音符位置上：

| 情况 | 音符时值 | 说明 |
|---|---|---|
| 命中 | 1/16 拍 | 轻，铺垫 |
| 完美斩 / 完美格挡 | 1/8 拍 | 明显一沉 |
| **终结斩** | **3/8 拍**（原 1/2 拍，试玩后调轻） | 稀有，重，但不打断整体律动 |

试玩反馈：手感成立。**顿帧只冻结画面与逻辑，绝不冻结音乐**——时钟读音频播放
位置，歌曲时间照常推进，解冻后画面直接跳到正确位置。

终结斩最初按"气满立即触发"实现，试玩发现会卡在乐句中间打断节奏感。
**决定：保留"气满触发"（当成奖励机制，不锁定必须在乐句末尾），
但把顿帧从半拍减到 3/8 拍**，在"有感知"和"不打断"之间取得平衡。

### 4. 节律必须由谱面驱动，机械周期不行 ✅ → 关键转向

最早版本：敌人机械地每 N 拍出招一次。**在拍网格上精确，但跟音乐的乐句
毫无关系**——明明每一下都在拍上，玩起来却别扭，不知道该在哪一拍出手。

**是玩家在试玩中自己摸索出问题所在的**（"我能做到的节奏只能是攻击、格挡、
攻击、格挡"），随后明确指出：节奏应该跟着音乐的乐句走（"跟着每一个字走"），
不能自动生成。

**尝试过自动生成谱面**（`make_draft_chart.py`，用 librosa 的 HPSS 分离打击乐、
在拍网格上采样强度选点），在硬派曲目（《霍元甲》98 BPM）上勉强能用，
**但在抒情曲（《牵丝戏》）上完全失败**——古风流行的节奏骨架在**人声**上，
不在鼓上，抒情曲的鼓又稀又软，基于打击乐强度的方法几乎抓不到信号。

调研佐证：学术界最好的自动谱面生成模型（Transformer + 1.4 万张谱面训练）
明确承认"在生成低难度稀疏谱面时彻底失败"——而稀疏正是抒情曲需要的。
剪映的自动卡点同样只做到"给候选 + 人工修"。

**最终决定：人工制谱，工具负责把人工做得舒服。** 做了 `chart_editor.tscn`：
分段循环播放、人声能量包络当背景参考（尖峰=字的位置）、边听边敲、
播放时音符自己发声跟音乐核对（"眼睛看不出 30ms 偏差，耳朵能"）、
鼠标点击选中/拖拽微调/右键删除。

**这不是退而求其次，是找到了对的方法**——制谱是内容创作，不是技术问题，
跟"一首歌能不能自动写完"是同一类不成立的期待。

### 5. 曲式驱动战斗结构：假设成立 ✅

用《牵丝戏》手工编排的 14 段谱面（137 个事件）接入完整曲式后试玩确认：
**这套编排玩起来是爽的**。主歌读招攒气、副歌 BOSS 破防（固定 2 倍伤害）、
音符轨道压扁铺在两角色之间（不做全屏掉落轨道，保持视线在战斗上）。

支柱二「一首歌就是一场战斗」成立，**但前提是谱面必须服务于乐句，
不能是机械网格**——这是本轮最重要的一条结论。

### 6. 武器差异化：原方案被推翻，改用「BOSS 干扰」✅

原支柱四「武器 = 音符密度和落点」（单刀一拍一刀、双刀一拍四刀）
**被证伪**：这只是难度分级（简单模式/困难模式），不是玩法差异。

讨论后改为：**每个对手用不同方式破坏你的节奏，而不是靠武器**——
中毒后 BPM 上升、老将逼你放弃密集连段、同路人预判连段、
人声干扰把拍子唱偏、终局军鼓压过曲子直到静音。
这是《余音》故事里已经设计好的五个对手，且是曲中剑和 Dead as Disco
都没有的维度。**锁定一把武器**，把手感调到极致，靠对手制造差异。

> 支柱四需要在 `game-concept.md` 中正式修订，见下方「待办」。

### 7. UI 迭代：从零提示 → 收缩环 → 音符轨道

- **零提示**（v1，敌人随机出招）：玩家不知道该干嘛
- **贴身收缩环**（v2）：密集节奏型时多个环叠在一起，人眼分不出先后
- **压扁的横向音符轨道**（v3，定稿）：铺在两角色胸口高度，判定线居中，
  蓝上红下，能看清疏密和先后，同时余光仍在两个角色身上（不违反
  「视线必须在敌人身上」的反支柱）

## 玩家反馈摘要（原样保留，供设计参考）

- "感觉还可以，还挺好玩的，有几个瞬间感觉打得还挺爽的"（早期节拍器版）
- "加了这个轨道之后好了很多耶！"（音符轨道取代收缩环之后）

- 终结斩应当是奖励机制，不必锁定乐句末尾，但停顿感要能被感知到、同时不能太长

## 下一步（留给正式设计 / 下一轮原型）

- **支柱四正式改写**：「武器改变的是数值」→「每个对手改变节奏本身」，
  并同步移除 GDD 中"武器=音符密度"的相关描述
- **视角对比**：2D 与 3D 受控侧视各做一版，仍未开始（见概念文档
  Visual Identity Anchor 一节）
- **谱面覆盖全曲**：目前只编了 14 段（约 112 秒），完整一首歌的制谱成本
  需要在正式生产阶段用 `chart_editor` 实测一次，估算每首歌的工时
- **对手干扰机制原型**：中毒变速、人声唱偏拍子等，尚未做任何一个的原型
- **自动谱面工具保留但降级为"仅供硬派曲目参考"**，不再作为主要路径
